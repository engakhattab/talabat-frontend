CHECKOUT 422 SAFETY RULE:

AppError.rawError has type unknown.

Do not rely solely on:

appError.rawError as CheckoutUnavailableResponse

A TypeScript assertion does not validate runtime data.

At the checkout boundary, implement the smallest approved runtime validation or
type guard necessary to prove that rawError has the documented
CheckoutUnavailableResponse shape before reading unavailableItems.

The validation must:

- reject null and primitive values
- verify that unavailableItems has the expected collection shape
- safely validate the fields actually consumed by the UI
- avoid unsafe access to malformed payloads
- fall back to the normal safe unknown-error path when validation fails
- remain local to the checkout-owned error boundary
- not weaken global Problem Details handling
- not require generated-client edits
- not spread raw HttpErrorResponse handling across components

Add focused tests proving:

1. A valid checkout 422 payload survives the interceptor.
2. A valid payload is recognized by the checkout boundary.
3. unavailableItems is presented correctly.
4. A malformed 422 body does not crash the application.
5. A normal Problem Details response remains mapped correctly.
6. An unknown 422 response follows a safe fallback path.
7. rawError is not rendered directly to the user.

CHECKOUT SUBMISSION SAFETY:

- One user submission must issue no more than one checkout request.
- Disable or lock the submission action while the request is active.
- Do not automatically resend after status 0 or another ambiguous failure.
- Preserve enough context for the user to inspect the cart or orders safely.
- A 201 response must trigger only the approved CartStore reconciliation.
- A 422 response must preserve the existing cart and recovery context.
- Session loss must not produce a false success state.
- Browser refresh on confirmation must use the approved server read path rather
  than transient navigation data only.
